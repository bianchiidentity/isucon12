# ベンチ後のpprotein・Kanbanレビュー

## 対象を決める

実行時の指定を優先する。未指定時の練習環境は次のとおり。

| 対象 | 既定値 |
| --- | --- |
| pprotein | http://localhost:9000/#/group/ |
| リポジトリ | bianchiidentity/isucon12 |
| Kanban | https://github.com/users/bianchiidentity/projects/3/views/1 |
| ベンチ結果の記録 | https://github.com/bianchiidentity/isucon12/wiki/Measurements |
| ベンチ結果JSON・ログ | サーバーの `/home/isucon/bench-results/` |

本番はURL・対象ホスト・計測対象・Projectを読み替える。ハードコードしたSSH先や秘密鍵を使わない。ローカルURLは手元からの転送先であり、他の読者にも届く公開URLではない。

## 1. どのベンチか確定する

- ユーザー指定の結果・グループを優先。なければ日時順に完了グループを確認し、ベンチ結果と対応付ける。API配列の最後が最新とは限らない。
- ベンチ日時（タイムゾーン付き）、スコア、PASS/FAIL、通常・Criticalエラー、稼働リビジョン、時間・台数・計測設定、グループIDを記録する。分からない項目は未確認と書く。
- このリポジトリの `scripts/bench-with-pprotein.py` が保存する結果JSONには、開始・終了時刻、結果、条件、pproteinのSnapshot情報がある。既存ファイルを読むために参照し、このレビューではスクリプトを実行しない。
- 同じ `Snapshot.GroupId` の対象が揃い、`Status=ok` か確認。収集時間が負荷走行と対応しているか照合する。Gitメタデータだけで稼働バイナリの版を断定しない。
- 失敗ベンチは性能改善の採用根拠にせず、エラー原因の調査を優先する。計測漏れ・対象ベンチ不明なら、取得できた事実と不足を報告し、断定的な並べ替えはしない。
- 前回比較は時間・台数・負荷・計測設定が一致する結果を選ぶ。計測なし1854点と全SQL記録ありの結果を同条件扱いしない。

## 2. 最新の計測を読む

画面操作より、保存済みの一覧・集計APIを優先し、独立した読み取りはまとめる。APIが使えない場合は画面から同じグループを読む。接続不能を「負荷なし」と解釈しない。

現在の導入版で確認済みの一覧は `GET /api/pprof`、`GET /api/httplog`、`GET /api/slowlog`、設定は `GET /api/group/targets`。一覧はメタデータなので、それだけで分析を完了させず、各Snapshotの集計内容まで取得する。集計API・画面リンクは導入版のソースや実際の画面から確認し、推測したURLを使わない。

**`/api/group/collect` はGETでも収集を開始するので呼ばない。** ベンチ後に新規収集しても、そのベンチのログにはならない。

| データ | 最初に読むもの | 判断上の注意 |
| --- | --- | --- |
| HTTP（alp） | 累積時間上位、回数、平均、P95/P99、ステータス内訳 | 累積時間を入口にするが、少数の遅い要求と大量の要求を区別。4xx・5xxの影響も見る |
| MySQL（slp） | 累積QueryTime、回数、平均、走査行数、LockTime | SQL全文と呼出元を照合。LockTimeだけで特定のロック競合と断定しない |
| SQLite（slp） | 累積時間、回数、返却行数、SQLと呼出元 | 現在のトレーサーは1ms未満が0。LockTime・RowsExaminedの0は未計測値 |
| Go CPU（pprof） | flat/cumulativeの上位関数、呼出経路 | CPUに出ないflock・I/O・接続待ちもある。親子のcumulative値は加算しない |

HTTPとSQLの累積時間は重なるので加算しない。SQLが速くても回数が多ければ候補に残す。処理件数が増えるベンチでは、累積時間だけで悪化と判断せず、平均・回数・要求当たりのSQL数も比較する。実測していない点数の伸びは予測しない。

上位3〜5個から掘り下げ、必要な場合だけ対象を広げる。全プロファイルの網羅的な読み込みやスクリーンショット作成は不要。計測方式の限界は `profiling/README.md` と現在の設定を確認する。

## 3. issueを実装と照合する

対象Projectの全item・列・順序・表示上のソート設定、関連issueの本文・最新コメント・状態、関連PRを取得する。ページネーションを最後まで読む。表示から隠れているitemや別リポジトリを混同しない。

各issueを次のいずれかに分類する。

- **優先**：今回の大きな負荷と、現コードの削減対象が結び付く。
- **継続**：仮説が残り、実装・検証する価値がある。
- **優先度低下／保留**：対象負荷が小さくなった、別施策で不要になった、または根拠不足。
- **実装済み・効果確認**：稼働版に変更が入り、今回の計測で対象処理の減少を確認できた。
- **再調査**：残存負荷・回帰・エラーがあり、従来の説明では足りない。

古いコード断片や画像と実装が違えば、その差をコメントする。依存する変更・同じ処理を狙うissueを確認し、重複効果を二重に見積もらない。負荷が消えただけでは「不要確定」にしない。低優先度と不要を区別し、再浮上する条件も残す。

## 4. Kanbanを更新する

基本は、未着手列で**現在の最大の負荷に対応するissueを上へ**。同じ負荷を狙う候補は、根拠の強さ・実装範囲・依存関係・リスクで順序を決める。エラー修正や必須の先行作業を先にする場合は理由を書く。ラベルが「小」だから常に先頭、とはしない。

Doing・Doneの列と状態、担当者は維持する。進行中issueにも分析結果はコメントする。解決済みの再発は関連issueへ報告し、勝手に再Openしない。保留候補は未着手列の下へ移す。Close・削除・Done移動・新規issue作成はこのSkillの既定動作に含めない。

GitHubは `gh api` を優先する。位置の更新はProject itemのIDを使い、issue番号と混同しない。現時点の操作方法は [GitHub公式のProjects GraphQLリファレンス](https://docs.github.com/en/graphql/reference/projects) を確認する。

- `updateProjectV2ItemPosition(input: {projectId, itemId, afterId})` で順序を更新する。`afterId` は直前itemのID。先頭に移す場合だけ省略する。
- 表示がフィールドでソートされている場合、位置変更だけでは見た目に反映されない。既存の順位用フィールドがあれば、その値で目的の順序を作る。Priorityが粗い区分だけなら同区分内の順序も確認する。表示設定の変更が必要なら、その変更を含む理由を明記する。
- 更新前の順序を保存し、対象の未着手itemだけを必要な分だけ動かす。変更直前に再読込し、他の人の変更があれば現在の状態へ統合する。
- Project権限が足りない場合は権限不足を明記し、並べ替え案と完了できた操作を残す。並べ替え済みと報告しない。利用可能な認証済みUIで操作できるなら続行する。

## 5. 変化のあるissueへ短く追記する

本文・画像・過去ログは書き換えない。順位・仮説・実装との対応・検証結果が変わったissueにだけコメントする。同じ結果を全issueへ貼らない。親issueがあれば、そこへ全体の上位候補と並び順を一度まとめる。親がなければ最終回答にまとめ、勝手に作成しない。

```markdown
<!-- bench-review:GROUP_ID:ISSUE_NUMBER -->
### ベンチ後レビュー：日時（TZ）／group ID
- 結果：スコア／PASS・エラー数／稼働版（不明なら未確認）
- 根拠：対象API・SQL・関数、回数・累積時間・P95等。比較可能なら前回 → 今回。
- 判断：優先／継続／保留／効果確認／再調査。その理由。
- Kanban：未着手列の旧順位 → 新順位、または変更なし。
- 次の一手：実装・追加計測で何を確かめるか。保留なら再検討条件。
- 出典：計測グループ・Snapshot ID、結果ファイル、稼働コードへのリンク。
```

同じgroup ID・issueのマーカーがあれば重複投稿しない。自分が投稿した同マーカーのコメントだけを必要に応じて更新する。投稿失敗時はコメント一覧を読み直してから再試行する。別のベンチは新しいコメントとして履歴を残す。

複数行のコメントはファイルに書いて `gh issue comment NUMBER --repo OWNER/REPO --body-file FILE`、またはJSONファイルを `gh api --input FILE` へ渡す。本文をシェルのコードとして展開しない。ログ全文・個人情報・資格情報は貼らず、判断に必要な集計だけを公開する。

## 完了の確認

変更後のProject順序・表示条件・コメントを読み戻す。最終回答は「今回の最大負荷」「次の上位3件」「保留にしたもの」「未確認事項」を短く示し、issueへのリンクを付ける。

一時データはgitignore対象の `.bench-review/` に保存する。ベンチ・収集・デプロイは実行せず、追加の図やスライドは作らない。git commit/pushを含む操作制限はリポジトリの指示に従う。
