# Issue図解の作成・公開

## 本文で理解し、図で確認できる構成

本文を読めば「何が問題で、何を変えるか」が分かり、図でその構造を確認できるIssueを作る。
説明を短い結論と画像だけにせず、図を見る前に具体例付きの説明を置く。
本文の長さと見出しは内容に合わせる。単純な改善なら数段落でよい。

説明は次の順を目安にする。

- **何を変えるか**：最初の一文を操作や動作で書く。「終了した大会の請求額を一度だけ計算して保存し、画面を開くたびの再計算をやめる」など。
- **今の処理と困る理由**：どの操作が、どのデータを、何回読むか。MySQL・SQLiteなど具体的な処理と結び付ける。
- **小さな具体例**：人数・金額・行・時刻などで変更の意味を示す。説明用の例と実測値を区別する。
- **変更後**：同じ例で減る処理と残す動作を説明する。
- **難所**：「整合性が必要」だけで済ませず、どの順序や境界で間違った結果になるかを一例で説明する。
- **今の実装との差**：古いIssueの案、既に適用した改善、今回まだ残る処理を区別する。最新コードを確認し、古い計測を現在の負荷として扱わない。

専門用語は必要な箇所で具体的な動作と一緒に説明する。「永続化」は再起動後も読めるようDBに保存すること、「確定」は以後の書き込みで請求が変わらない状態、など。
説明用の本文は折りたたみの外に置く。根拠ログ・コピーできるコード・確認条件はその後に残す。

### 本文と図の分担例：請求の確定保存

本文では、毎回MySQLの閲覧者とSQLiteのスコア登録者を読み、参加者100人・閲覧だけ20人なら10,200円を繰り返し計算することを説明する。
変更後は確定額を保存して読むだけになる。ただし終了が12:00:00.100、閲覧が12:00:00.800でも秒単位では同じ12:00:00となり、現在の判定では閲覧も対象に含む。終了直後に固定すると取りこぼす、という難所まで本文で説明する。

改善の図では「請求画面を開く → 登録者100人と閲覧だけ20人を読み、10,200円を計算」を、画面を開くたびに繰り返す様子を示す。変更後も同じ例を使い、「一度計算して保存 → 次から保存した人数と10,200円を読む」と並べる。
学びの図では別の論点として「終了直後に10,200円を保存 → 終了と同じ秒の閲覧者がもう1人 → 正しくは10,210円」を時間軸で示す。その具体例から「結果を保存して再利用するには、対象の書き込みが揃う条件を決める必要がある」という技術的な学びへつなげる。
「永続化」「確定条件」「整合性」などの抽象語だけを箱や矢印に置いて説明したことにしない。
本文の全段落を画像に詰め込まない。この例の料金・時刻・確定条件は対象の仕様に照らして確認し、他のIssueへ固定の前提として持ち込まない。

### 学びの図の内容と表示位置

- **具体例 → 起きる結果 → 技術的な学び**の順で構成する。誰のどの操作で、どのデータ・人数・金額がどう変わるかを図にも明記する。説明用の値は実測値と区別する。
- **改善の図と学びの図は役割を分ける。** 改善の図は「何が繰り返され、何を減らすか」、学びの図は「どの具体的なケースで間違い、どの技術・条件が必要になるか」を伝える。両方を扱う必要があれば2枚に分け、1枚へ詰め込まない。
- 学びの図は独立した **`## このIssueで学べること`** に置き、折りたたまず表示する。短い具体例と学びの結論を添える。補足図や原文保存用の `<details>` に隠さない。
- 既存Issueの順序は依頼なく変えない。学び欄がなければ、本文末尾の原文保存用detailsより前に追加する。折りたたみから移す依頼なら、その位置で見出しを独立させ、他の節は維持する。
- **本文を隠して図だけを見ても意味が通るか**を確認する。「誰が何をした → 何が起きた → なぜこの技術が必要か」を説明できなければ、具体例・順序・結果を書き直す。見た目が良くても内容が伝わらない図は完成扱いしない。

## 読者と書き方

原則は「1 issueにつき学びの図を1枚」。改善の説明と学びが異なる論点になる場合や、競合・復旧を別に説明する必要がある場合は2枚にする。ログ表・コード・実装範囲・確認項目・結果記録はMarkdownで残し、画像化しない。完成済みの承認された図は再利用する。全段落をスライドにする方式は、明示的に頼まれた場合だけ使う。

プロの技術者が、根拠・変更・制約を短時間で判断できる説明にする。
論理名（物理名）の順で書く。例：CSV内の行番号（row_num）。コード内の識別子は変えない。
「左の列」など曖昧な説明を避け、複合インデックスのキー順序など正しい用語を使う。
1枚1論点。段落を画像に貼るだけでなく、処理順・データ配置・変更前後の差を図にする。
小さな文字に縮めず、複雑な競合・失敗・初期化の説明は別スライドに分ける。

## 作業手順

1. `gh api repos/OWNER/REPO/issues/NUMBER`で本文を保存し、対象コードとログを確認する。
2. 観測事実と未確認の原因を分ける。HTTPとSQLの累積時間を加算しない。改善点数を予測しない。
3. 最新コードと既存施策を照合し、上の順序を参考に具体例付きの本文を先に書く。その後、根拠ログ・コード・実装範囲・確認条件を整理し、本文だけでは関係を捉えにくい部分を図の題材にする。
4. [承認された見本：issue #4](https://github.com/bianchiidentity/isucon12/issues/4) の画像を実際に表示して確認する。大きな結論、青・ティールの意味のある強調、具体的なデータ表、比較、分岐・時系列を基準に構成する。
5. 各スライドに固有の図と短い原稿を作る。画像生成機能を使い、見本画像をスタイル参照として渡す。Codexではimagegen、Claudeでは利用可能な画像生成機能を使う。利用できない場合はその制約を伝え、黙って低品質のテンプレートへ置き換えない。
6. 全PNGを目視確認する。日本語・SQL・数値に加え、強調の階層と図の正しさを確認する。見本より劣る場合は公開前に直す。生成物は `.issue-slides/` にコピーし、公開用manifestへ画像のタイトル・パス・ハッシュ付きファイル名を保存する。
7. 確認済み画像を `issue-N-PP.png` として保存する。プロンプト一覧（JSON配列。number/page/title/prompt）を保存し、`python3 scripts/issue-slides/package.py .issue-slides/prompts.json .issue-slides/reviewed` でハッシュ付き画像とmanifestを作る。公開を依頼されている場合、`python3 scripts/issue-slides/publish.py --repo OWNER/REPO --manifest .issue-slides/reviewed/manifest.json --snapshot .issue-slides/issues-before.json --publish`で公開する。`--publish`省略時はプレビューのみ。
8. issue本文・画像URL・原文保持を読み戻して検証する。学びの図が独立した見出しにあり、detailsの外に表示されていることも確認する。ベンチ実行やコード変更は別依頼として扱う。

## 速く更新するための分担

図は構造の理解に使い、更新頻度の高いログ・コード・結果はMarkdownにする。既存の図の説明が変わらなければ再生成しない。原稿で数値・識別子・保存先・矢印の意味を確定してから生成し、修正生成を減らす。独立した画像は並行生成し、公開はCLIでまとめる。

`spec.example.json` は画像生成用プロンプト一覧の例。パッケージ後のmanifestには、issueごとに `intro_md`（具体例付きの説明本文。複数段落・見出しを含めてよい）と `after_images_md`（根拠ログ・コード・実装範囲・確認項目）を追加できる。公開スクリプトはこのMarkdownと画像を表示し、元の本文を別のdetailsに保存する。

## Gitと公開先

画像・生成HTML・スナップショットは `.issue-slides/` に置く（gitignore対象）。GitHubの専用Release `issue-diagrams` に画像を添付し、issue本文から参照する。通常のclone/pullは添付画像を取得しない。画像をコードブランチにcommitしない。
Releaseは既存HEADを対象とし、新しいアプリ用コミットを作らない。公開前に当該リポジトリのルール・権限を確認する。
生成画像は内容ハッシュ付きの名前にする。過去画像を削除しない。再生成用のspecもReleaseへ添付する。

## 元の説明を守る

原文・コード・リンクは一字も失わずdetailsへ残す。既存の図解は原文と分離して更新する。
公開直前に取得本文が保存済み本文と一致するか確認する。競合時は停止して最新本文へ統合する。
失敗した場合は状態を確認して再実行する。公開済みの同内容画像は再利用する。
画像だけに情報を閉じ込めず、テキストの説明とコピーできるSQLを残す。

## 品質基準

- 固定の二カラムカードへ文章を流し込む方法は不採用。`scripts/issue-slides/render.mjs` は旧試作であり、承認された完成品質の生成方法ではない。
- 最初に見えるのは大きな結論。本文・図のラベル・脚注には明確な文字サイズの差をつける。均一な太さ・色・サイズにしない。
- 図は具体的なデータや状態を描く。N+1なら人数分のSQLへの分岐、索引なら行の並びと走査範囲、Txならcommit/rollbackの時間軸、分散ならホストとデータ配置を描く。
- 単に同じ文章を矢印付きの箱へ移さない。読む順序、回数、関係、境界が視覚だけでも分かる図にする。
- 文章の段落数を枚数にしない。重複する学び・適用・注意を統合し、難しい失敗例や競合は追加の1枚に分ける。
- 速度のために生成方法や見た目を勝手に変更しない。アップロードはCLIで効率化するが、図解の品質は見本を維持する。

- 図を非表示にしても、操作・現在の処理・変更後・難所を具体例で説明できる。画像には関係・回数・時間軸があり、本文の文章をそのまま箱に流し込んでいない。
- 読み手が「何が遅いか」「どの処理を減らすか」「何を壊してはいけないか」を説明できる。
- 学びは一般的な技術原理と今回の適用がつながっている。入門用の比喩や理解度クイズに置き換えない。
- 全体説明は重複をまとめる。複雑さに応じて枚数を増やし、固定枚数へ詰め込まない。
- 出典リビジョンと実装案を区別する。古いコードを現在の稼働版と断定しない。
- 実測していない改善を、完了チェックや効果保証として描かない。
